# How it is computed

Cribelo ranks the files of a change by one number, the probability that a human should read them. This page gives every step that produces that number, so that you can contest it. Methodology version 1.1; the version is bumped whenever a signal, a transform or a default weight changes, and a weights file from another version is ignored.

## The change

The change is the diff between the merge-base of your branch and the base branch, and your working tree, untracked files included. The base branch is the one you pass with `--base`, else the one in `.cribelo.yaml`, else `origin/HEAD`, else the first of `origin/main`, `origin/master`, `main`, `master`, `origin/develop`, `develop` that exists.

For each file the diff gives a status, the lines added and deleted, and the hunks, the ranges of lines that were touched.

## Files set aside

Some files never get a score. They are listed under Skip with their label.

| Label | Rule |
|---|---|
| tests only | the path looks like a test (`_test.go`, `*Test.php`, `test_*.py`, `*.spec.ts`, `tests/`, `__tests__/`...) |
| generated | the path matches a generated pattern (`vendor/`, `node_modules/`, `*.pb.go`, `*.min.js`, lock files...), or a comment in the first kilobyte says `generated`, `do not edit` or `autogenerated` |
| renamed | moved without a content change |
| deleted | removed from the tree |
| binary | git sees no text |
| not analyzed | an extension outside `.go .php .py .rs .ts .tsx .java .cs` |
| no measurable change | parsed, but every signal below is zero |

Globs in the `ignore` list of `.cribelo.yaml` are dropped before anything else.

## Ten signals

The remaining files are parsed, after and before the change, with the tree-sitter engines of AST Metrics. A function is touched when its line range crosses a hunk. New functions are matched by name against the previous version of the file.

| Signal | Source | Value |
|---|---|---|
| lines_added | diff | lines added |
| lines_deleted | diff | lines deleted |
| complexity_added | AST before and after | sum over touched functions of the cyclomatic complexity gained; a new function counts its complexity minus one |
| max_complexity | AST after | highest cyclomatic complexity among touched functions |
| afferent | import graph of the repository today | number of files outside the file's own directory that import it |
| fixes_90d | git log | fix commits that touched the file in the 90 days before the change |
| churn_90d | git log | all commits that touched the file in the same window |
| new_file | diff | 1 when the file did not exist at the base |
| untested | tree | 1 when no test file shares its stem in its directory, or contains the stem when it has at least three characters |
| clone_similarity | function index of the repository | highest Jaccard similarity between a touched function and any other function elsewhere, 0 when below 0.70 |

Cyclomatic complexity follows the shared decision model of AST Metrics: the same construct scores the same in every language.

The clone check tokenizes the body of every function of the repository, except tests and generated files. The declaration is left out: once identifiers are normalized, every parameter list looks like every other one, and a constructor with promoted properties would pass for a clone of any data holder. Identifiers become one symbol, numbers another, comments are dropped, and string literals keep their content: a function copied and adapted keeps its strings, while the mapping boilerplate of two data holders (`toArray`, a configuration block) differs by its keys and must not count. Every run of seven tokens is hashed and a fingerprint is kept by winnowing (window of four). Two bodies of at least sixty tokens that share at least 70 % of their fingerprints are clones. A function is compared only to candidates that share at least 35 % of its fingerprints, which keeps the check linear in practice.

## The score

Counts are compressed with `log(1 + x)`, so that the tenth line matters more than the thousandth. `new_file`, `untested` and `clone_similarity` are used as they are. Each transformed value is standardized with the mean and standard deviation stored in the weights file (0 and 1 for the defaults), multiplied by its weight, and the sum plus an intercept goes through the logistic function:

```
score = 1 / (1 + exp(-(intercept + Σ weight_i · (transform_i(x_i) - mean_i) / std_i)))
```

Default weights:

| Signal | Weight |
|---|---|
| lines_added | 0.35 |
| lines_deleted | 0.10 |
| complexity_added | 0.50 |
| max_complexity | 0.30 |
| afferent | 0.40 |
| fixes_90d | 0.60 |
| churn_90d | 0.20 |
| new_file | 0.30 |
| untested | 0.50 |
| clone_similarity | 1.50 |
| intercept | -4.0 |

A score of 0.70 or more is high, 0.40 or more is medium, below is low. The thresholds are stored with the weights. The files are sorted by score; ties are broken deterministically, so the same change always gives the same order.

The reading list is every file at the high level, and at least `top` files (three by default, also a key of `.cribelo.yaml`). `--top N` on the command line reads exactly N files. `--budget` reads as many files as fit in the given time at twenty changed lines a minute, and overrides both. The list is never empty when a code file was ranked. The reasons printed next to a file are its three largest positive contributions.

`cribelo explain <file>` prints every value and contribution of one file.

## The backtest

`cribelo backtest` walks the first-parent history of the base branch, newest first, up to `--max` landings among those at least ninety days old (a busy branch may have hundreds of younger ones). For each landing (a merge, or a commit landed directly) it rebuilds the change against its parent, parses both snapshots from git objects, computes the ten signals and the plan. A landing qualifies when it changes at least four code files and is old enough for the ninety days that follow to be known.

A file counts as fixed when a commit whose message is recognized as a fix touches it in the ninety days after the landing. A message is a fix when it holds, as a whole word, one of: `fix fixes fixed fixing hotfix bugfix bug revert regression`, their French, Spanish, Portuguese and German counterparts, the conventional commit types `fix:` and `revert:`, the gitmoji 🐛 🚑 🩹 ⏪ or their shortcodes, or the `fix_pattern` of `.cribelo.yaml`. Letters on either side break the match: `fixture` and `prefix` are not fixes.

Two numbers come out. Coverage: among the files later fixed, the share that was in the reading list. Lines: the share of the changed lines the reading list asked you to read. They are given for three reading lists: the top `top` files, the rule the plan applies (every high file, at least `top`, with the average number of files it reads per change), and the naive plan of reading the largest files, so that you see the gain.

Two approximations. The import graph is today's, not the one at the time of the landing. Clones are not replayed.

## Calibration

`cribelo calibrate` runs the backtest, then splits the qualified changes chronologically: the oldest 70 % train, the most recent 30 % test. It needs at least thirty changes and ten later-fixed files. A logistic regression (3000 iterations of gradient descent, learning rate 0.1, L2 penalty 0.01, features standardized on the training set) learns the intercept and nine weights; the clone weight stays at its default, because clones are not replayed.

A learned model outputs the probability of a later fix, which is low when fixes are rare, so the fixed thresholds of 0.70 and 0.40 would leave the high level empty. The learned model therefore gets its own thresholds, chosen on the training files so that it flags the same share of files high, and the same share medium, as the generic model does. A level keeps its meaning of "the riskiest files of the change".

The learned weights and thresholds are scored on the test split with the coverage measures of the backtest, and written to `.cribelo/weights.json` only when they cover at least as many later-fixed files as the defaults there, both with the top `top` files and with every high file. Otherwise nothing is written and the output says so.

The weights file records the methodology version, the number of changes it was trained on and the date. Commit it; every plan picks it up.

## What a label means

"Later touched by a fix" is not "the bug was in these lines". A fix commit may touch a file to adapt it to a repair made elsewhere. The label is noisy in both directions, which is why the backtest reports it as a share rather than a verdict, and why Cribelo says "nothing measurable changed" rather than "safe".
